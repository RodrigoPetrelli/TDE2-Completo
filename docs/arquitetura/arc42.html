1. Introdução e Objetivos

O PedeJá é uma plataforma de pedidos de delivery de restaurantes. Clientes consultam cardápios e fazem pedidos; restaurantes parceiros mantêm o cardápio e confirmam ou cancelam pedidos; a plataforma notifica as partes a cada mudança. A versão de partida era um único arquivo de rotas Express, com validação, regras de negócio, acesso a dados e notificação dentro dos handlers. Este documento descreve a arquitetura-alvo e a refatoração entregue no repositório, que aplica os estilos arquiteturais pedidos: Serverless, Microfrontends, BFF + Microsserviços + Database per Service, API Gateway, Arquitetura Orientada a Eventos, Clean Architecture com Vertical Slice e Testes Unitários de Arquitetura.

4.1 Software Architecture Canvas

Proposta de valor

Pedir comida de restaurantes locais de forma rápida e confiável, com total transparente (subtotal + R$ 7,90) e aviso imediato ao restaurante.

Stakeholders principais

  • Clientes
  • Restaurantes parceiros
  • Times Catálogo, Clientes, Pedidos e Front
  • Operação / SRE

Requisitos de qualidade

  • Manutenibilidade (fatias isoladas)
  • Escalabilidade elástica nos picos
  • Resiliência a falhas de notificação
  • Deploy independente
  • Conformidade verificada por testes

Contexto de negócio

Marketplace de delivery com picos nas refeições; restaurantes independentes; notificações por e-mail/push; autenticação via provedor externo.

Funcionalidades centrais

  • Catálogo: restaurantes e cardápio
  • Cadastro de clientes
  • Pedido com regras e máquina de estados
  • Notificações por eventos
  • Telas agregadas (BFF)

Tecnologias

  • TypeScript, Node.js 24, Express
  • AWS Lambda, API Gateway, EventBridge
  • DynamoDB, S3 + CloudFront, SNS/SES
  • Jest + compilador TS (testes de arquitetura)
  • PlantUML / C4-PlantUML

Componentes

  • Shell + MFE Catálogo + MFE Pedidos
  • API Gateway
  • BFF Web, BFF Mobile
  • Serviços Catálogo, Clientes, Pedidos, Notificações
  • Barramento de eventos; 4 bancos

Decisões centrais

  • Database per Service com réplicas por eventos (ADR-002)
  • Clean Architecture + Vertical Slice (ADR-004)
  • Regras verificadas por testes (ADR-005)
  • Serverless na AWS (ADR-006)

Riscos e informações em aberto

  • Consistência eventual das réplicas
  • Sem outbox: evento pode se perder se a publicação falhar
  • Autenticação ainda não implementada
  • Persistência local apenas em memória

8. Conceitos Transversais

8.1 Modelo de dados e Database per Service (DER)

Cada serviço é dono do seu banco. Relações entre bancos são apenas referências lógicas (ids), sem chave estrangeira física. O Serviço Pedidos guarda réplicas mínimas (restaurante, produto, cliente) alimentadas por eventos e faz snapshot de nome e preço em item_pedido, para que mudanças futuras no cardápio não alterem pedidos já feitos.

8.3 Regras de Clean Architecture e Vertical Slice

  • domain: entidades, agregados e regras; não importa nada fora de domain nem frameworks.
  • application: portas (interfaces) de repositórios e plataforma (BarramentoEventos, Relogio, GeradorId).
  • features/<fatia>: <fatia>.ts é o caso de uso (sem HTTP); <fatia>.http.ts é o adaptador de entrada, que só traduz HTTP e delega. Uma fatia não importa outra.
  • infrastructure: implementações das portas, instanciadas somente pela composition root do próprio serviço.
  • composition roots: <servico>.service.ts (local), lambda.ts (serverless) e app.ts (processo local completo).

8.4 Testes unitários de arquitetura

Os testes de arquitetura leem os imports de todos os arquivos de src/ com ts.preProcessFile, do compilador TypeScript, e verificam as regras abaixo. 8.5 Tratamento de erros

O domínio lança ErroValidacao, ErroNaoEncontrado ou ErroRegraNegocio, que não conhecem HTTP. O adaptador shared/http/tratador-erros.ts mapeia esses erros para 400, 404 e 422; JSON malformado vira 400 e o restante, 500. Os BFFs repassam ao front o status e o corpo do serviço chamado (ErroServico).

8.6 Segurança, observabilidade e configuração

  • Correlation id: o gateway gera ou propaga x-request-id, e os BFFs o repassam nas chamadas aos serviços.
  • Rate limiting: janela fixa por IP no gateway (HTTP 429); na nuvem, throttling do API Gateway.
  • Roteamento observável: cabeçalho x-servico indica o destino da requisição.
  • Autenticação (planejada): autorizador JWT do API Gateway com Amazon Cognito.
  • Menor privilégio: cada Lambda tem papel IAM com acesso apenas às próprias tabelas, o que reforça o Database per Service.
  • Configuração: PORT e SERVICOS_URL por variáveis de ambiente.

9. Decisões de Arquitetura

ServerlessModelo de execução sem gestão de servidores (AWS Lambda), cobrado por uso.
